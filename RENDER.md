# Deploying to Render — zero-touch

This repo ships a [Blueprint](./render.yaml) that deploys the whole app as **one service**:

- **kitchenlovers-ecom** — Node web service. Express + Socket.IO serve the API *and* the
  built React PWA from `client/dist`, on a single origin. A 1 GB disk is mounted at
  `/var/data/uploads` as a fallback image store.
- **kitchen-ecom-secrets** — shared env group; you fill it in once.

Single-origin matters: because the frontend and API share a hostname, the client needs no
`VITE_API_URL` (it defaults to `/api`) and there are no CORS or cookie-domain problems.

What's automatic:

- `npm install --include=dev && npm run build` builds `client/dist` during deploy; the server
  finds it by probing several candidate paths, so it works regardless of Render's `rootDir`.
- JWT secrets are generated by Render (`generateValue: true`).
- Roles, super-admin, sample categories, and the storefront setting are seeded on every boot
  (idempotent — `AUTO_SEED=true`).
- `NODE_VERSION` is pinned to 20, matching `.nvmrc`.

MongoDB and Cloudinary live outside Render — both have free tiers that are enough.

## One-time setup (≈ 5 minutes)

### 1. Atlas (database)

1. Atlas → new project → **M0 Free** cluster.
2. Database Access → add a user (note the password).
3. Network Access → **Allow access from anywhere** (`0.0.0.0/0`) — Render outbound IPs aren't
   fixed on lower plans.
4. Cluster → Connect → Drivers → copy the `mongodb+srv://…` string. Replace `<password>` and
   append the DB name, e.g. `/kitchen_ecom?retryWrites=true&w=majority`.

### 2. Cloudinary (product images)

1. [cloudinary.com](https://cloudinary.com) → sign up (free tier is plenty).
2. Dashboard → **Product Environment Credentials** → copy the cloud name, API key, API secret.

Uploads land in `kitchenlovers/products`, `kitchenlovers/categories`, `kitchenlovers/banners`.

### 3. Apply the Blueprint

1. [Render Dashboard](https://dashboard.render.com) → **New +** → **Blueprint** → pick this repo.
2. Render reads `render.yaml` and prompts for the `kitchen-ecom-secrets` values.

### 4. Fill the env group (the only thing you type)

| Key | Value |
| --- | --- |
| `MONGO_URI` | the Atlas connection string from step 1 |
| `CLIENT_URL` | `https://<your-service>.onrender.com` — the service's own URL (comma-separate to add a custom domain) |
| `CLOUDINARY_CLOUD_NAME` | from step 2 |
| `CLOUDINARY_API_KEY` | from step 2 |
| `CLOUDINARY_API_SECRET` | from step 2 |
| `SEED_SUPER_ADMIN_PHONE` | e.g. `+233500000000` (E.164 with `+`) |
| `SEED_SUPER_ADMIN_PASSWORD` | a strong password — your login |
| `ARKESEL_API_KEY` | leave blank for stub mode (OTPs printed to logs) |
| `PAYSTACK_SECRET_KEY` | leave blank for stub mode (auto-success checkout) |
| `PAYSTACK_PUBLIC_KEY` | leave blank for stub mode |
| `PAYSTACK_WEBHOOK_SECRET` | leave blank for stub mode |
| `VITE_PAYSTACK_PUBLIC_KEY` | same as above, blank for stub |
| `VITE_WHATSAPP_NUMBER` | E.164 digits only, no `+`, e.g. `233240000000`. Blank if unused. |

Also set `PUBLIC_URL` on the service itself to the service's public URL (already in
`render.yaml` — update it if you rename the service or add a custom domain).

Every blank optional key degrades to a documented stub rather than failing the boot, so a
partially-filled group still deploys.

### 5. (Optional) Paystack webhook

With live Paystack keys, set the webhook in Paystack Dashboard → Settings → API Keys & Webhooks:

- URL: `https://<your-service>.onrender.com/api/payments/webhook/paystack`
- Use the same secret you put in `PAYSTACK_WEBHOOK_SECRET`.

## Verifying the boot

The startup log states which mode every integration is in. A healthy production boot:

```
[db] connected: …mongodb.net/kitchen_ecom
[server] frontend -> serving /opt/render/project/src/client/dist
[server] media origins (csp img-src + connect-src) -> https://res.cloudinary.com
[server] cloudinary: live (cloud "…")
```

If you see `[server] cloudinary: DISABLED`, one of the three `CLOUDINARY_*` vars is blank and
new uploads will go to the fallback disk instead of the CDN.

If you see `[server] frontend -> API only (no client/dist found)`, the Vite build didn't run —
check that `buildCommand` still passes `--include=dev` (Render sets `NODE_ENV=production`,
which otherwise makes npm skip the devDependencies that Vite lives in).

## Smoke test

1. Open the service URL. Home loads with categories and banner images.
2. Sign in as super admin with `SEED_SUPER_ADMIN_PHONE` / `SEED_SUPER_ADMIN_PASSWORD`.
3. Register a separate test account. In stub mode the OTP appears in the service logs; in live
   Arkesel mode it arrives via SMS.
4. Upload a product image in admin. The returned URL must start with
   `https://res.cloudinary.com/` — if it starts with `/uploads/` or your own hostname,
   Cloudinary is not configured.
5. **Reload the page twice.** The first load runs without a service worker; the second runs
   with it. Images must be visible on both. This is the check that catches the CSP class of
   bug described below.
6. Place a test order. Stub mode → `/checkout/stub-pay`. Live Paystack → real checkout.

## Images and the service worker — read before touching CSP

Product images are served from `res.cloudinary.com`, and the service worker caches them. That
combination requires the Cloudinary origin in **two** CSP directives, for two different reasons:

- `img-src` — the page renders `<img src="https://res.cloudinary.com/…">`.
- `connect-src` — the service worker re-issues that same request with `fetch()` from inside the
  worker, and `fetch()` is governed by `connect-src`, never `img-src`.

Miss it from `connect-src` and the failure is nasty: the **first** visit works (no service
worker yet), then every image on the site breaks from the second visit onward, because the
worker's fetch is blocked and `respondWith()` rejects. Pasting the image URL into a browser tab
still works, which makes it look like a frontend bug.

Both directives are built from one `MEDIA_ORIGINS` array in
[`server/src/index.js`](./server/src/index.js) so they cannot drift. **Add new image CDNs to that
array, not to the directives individually.**

The worker ([`client/src/sw.js`](./client/src/sw.js)) adds two further guards:

- Cross-origin images are re-fetched in `cors` mode so responses have a real status. Plain
  `no-cors` responses are *opaque* (status 0, indistinguishable from a 404), and caching those
  pins broken images for the full 30-day TTL.
- Every route is wrapped in `failOpen`, so a strategy that throws falls back to a direct network
  request instead of returning a broken response.

## What lives where

| Concern | Location |
| --- | --- |
| HTML/JS/CSS bundle | served by the Node service from `client/dist` |
| API + WebSocket | same Node service, same origin |
| MongoDB | Atlas (external) |
| Product images | Cloudinary CDN |
| Fallback image storage | Render disk at `/var/data/uploads` (empty when Cloudinary is on) |
| Refresh tokens, sessions | MongoDB (no Redis needed) |
| Shared secrets | Render env group `kitchen-ecom-secrets` |

## Custom domains

1. **Service → Settings → Custom Domains** → add e.g. `shop.example.com`.
2. Update the env group / service vars:

| Key | Value |
| --- | --- |
| `CLIENT_URL` | `https://shop.example.com,https://<service>.onrender.com` (comma-separated keeps both working) |
| `PUBLIC_URL` | `https://shop.example.com` |

Redeploy. No `VITE_*` URL changes are needed — the client talks to `/api` on whatever origin
serves it.

## Cost snapshot (USD)

- Web service: Starter $7/mo (Starter is required to attach a disk).
- Disk: 1 GB ≈ $0.25/mo.
- MongoDB Atlas M0: free.
- Cloudinary free tier: free.
- **Total: ~$7–8/mo.**

Now that images live on Cloudinary the disk is only a misconfiguration safety net. Dropping the
`disk:` block lets the service run on a cheaper plan — but Render deletes the disk when you
remove it, so only do that once you've confirmed nothing under `/var/data/uploads` is still
referenced (`db.products.find({ "images.url": /^\/uploads/ })` should return nothing).

## Re-running the seed manually

Auto-seed runs on every boot. To invoke it by hand, open **Service → Shell**:

```
npm run seed
```

To disable auto-seed entirely, set `AUTO_SEED=false`.

To move any legacy local `/uploads/*` images onto Cloudinary:

```
npm run migrate:cloudinary --workspace server
```

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| Images load on the first visit, break on every later visit | `res.cloudinary.com` missing from CSP `connect-src` — the service worker's fetch is blocked. See the CSP section above. |
| Images broken and stay broken after a fix | A previous worker cached opaque error responses. `cleanupOutdatedCaches()` plus `skipWaiting()` clears them on the next deploy; to force it now, DevTools → Application → Storage → Clear site data. |
| Admin upload returns a `/uploads/…` URL | A `CLOUDINARY_*` var is blank. Check the boot log for `cloudinary: DISABLED`. |
| `Network Error` in the browser | The service didn't build `client/dist`, so the SPA fell back to the API JSON banner. Check the build log for the Vite step. |
| API logs: `CORS: origin … not allowed` | `CLIENT_URL` doesn't include the origin you're browsing from. It accepts a comma-separated list. |
| API logs: `Missing required env var: MONGO_URI` | Env group not linked. Confirm `kitchen-ecom-secrets` is bound under Environment. |
| Login works but refresh fails | Clock skew or rotated `JWT_REFRESH_SECRET`. Delete the env var and redeploy — `generateValue` recreates it. |
